## 这场对话要回答什么问题

一位网名 Potato 的工程师在一个月内向生产环境提交了 2,500 个 Pull Request，并把这个过程做成了演讲。演讲在 X 上获得约 300 万次观看，约 10 天之后，主持人 Matt 与他坐下来逐条追问。两人都以编写 AI 编程技能（skill）闻名，所以这次对话的实际内容不是经验分享，而是把一整套工作方法拆开对照。

读者读完后应该能回答一个问题：从"亲自盯住一个 agent 写代码"到"睡着时 agent 仍在合并代码"，中间需要依次跨过哪些台阶，每一级台阶的前置条件又是什么。

### 起点：一个人被一个 agent 拖住

讲者的路径从 Meta 的 React 团队开始。他因为倦怠休假一个月，按他自己的说法，倦怠时最自然的事就是开一个新项目。他用 AI 写代码，很快发现自己把大量时间花在"微观管理一个 agent"上。同一时期，社区的热门话题是编排（orchestration）：人们在终端里讨论如何自建一个 orchestrator。讲者被这个问题吸引，因为他真正想解决的是"怎样让 AI 编程环境更有效率"。

这里出现了第一个值得注意的失败模式。他在反复迭代技能，却无法衡量这些技能对产出或结果的实际影响。他当时的原话是"flying blind"——在盲飞状态下快速迭代。这个项目后来成为 pstack 的基础，尽管他当时并不知道。相关技能与一个 `brain` 目录至今仍开源在 GitHub 的 `potato/noodle` 仓库中。

他后来才把当时的动机讲清楚：他想把自己的能力提取出来交给 agent，本质上是"教 agent 用更像我的方式写代码、用更像我的方式跑流程"。

### "肉代理"：瓶颈位置的第一次确认

加入 Cursor 之后，他负责 agents window 的性能问题。因为有过 React 的经验，他被邀请去优化这个界面。工作方式是高度手工的：看火焰图（flame graph）、看堆快照（heap snapshot），逐个判断应用为什么卡。

重复几轮之后，他得到与做个人项目时相同的结论——他自己才是瓶颈。他用了一个很精确的说法：他是 agent 与 Chrome DevTools 之间的"肉代理"（meat proxy）。工具本身是可编程的，但他把指令从一边人工搬到另一边。

> 🔑 **要点：瓶颈不在模型，在人的位置**
>
> 当模型能力上升而流程没有变化时，瓶颈会从"agent 不够聪明"转移到"人被放在了不该由人承担的位置"。判断自己是否处于这个状态，只需要看一件事：你是不是在把机器可执行的动作，用自己的判断力一个接一个地搬过去。

值得记下时间线：他在 3 月加入，早期版本的工作大约发生在 4 月初。那段时间他一度放弃了自己积累的个人技能，认为它们不再适用；后来在 agents window 和新项目 Grokbot 上，他发现这些技能里关于验证与严谨性的部分依然成立。

### 领域专长为什么反而更重要

主持人提出了一个流行的疑问：当大家越来越依赖 AI，领域专长是否正在贬值。讲者的回答相反。

他的推理链是：模型越强，瓶颈越不在 agent 一侧，而在"你能否把意图和目标表达成 agent 能理解并执行的形式"。如果一个人具备领域专长，同时又有一点技术能力、能学会使用 agent，那么只要他脑中的愿景足够清晰，并且能把它表达出来，他就能做出很好的产品。按这个推理，领域专长的价值体现在表达质量上，而不是体现在手写代码的速度上。

> 💡 **知识点：一个容易被误读的结论**
>
> "领域专长更重要"并不等于"技术细节不重要"。讲者的限定条件是"有一点技术能力、能学会用 agent"。缺少这一环，专长无法转化成可执行的指令，瓶颈仍然留在人身上。

### 语言成为与 agent 的接口

主持人对语言本身有长期兴趣，他提到自己不断思考词句的组合方式，以及一个短语里可能藏着什么。讲者补充了一个可观察的现象：当你找到一个 agent 会"钩住"的词，它就会在后续的推理轨迹（thinking trace）里反复复用这个词。因此选词不只是文风问题，它会改变 agent 的行为。

两人都把自己的语言训练与 agent 工作连了起来。讲者提到自己有戏剧学背景，长期思考语言与莎士比亚；主持人则指出编程语言与自然语言如今在 agent 这里合流——两者都是语言，都是沟通。

### 本章小结

这场对话要回答的是"台阶"问题：怎样从被一个 agent 拖住，走到自己不在回路里。第一级台阶的前提是承认瓶颈在人这一侧；第二级台阶的前提是承认领域专长的价值转移到了表达上；第三级台阶的前提是承认语言是新的接口层，选词会改变 agent 的行为。下一章要处理的是：既然语言和流程如此重要，为什么"工厂"这个比喻仍然不够用。

## 为什么"米其林厨房"比"软件工厂"更贴切

"软件工厂"（software factory）是这场讨论的关键词。讲者明确表示他不喜欢这个词，理由不是它不准确，而是"工厂"这个词往往会带来负面联想，并且容易引导人把注意力放到流水线和产量上。他改用米其林厨房来组织思路。

### 工厂隐喻丢失了什么

工厂隐喻擅长描述重复与吞吐，但它不擅长描述一件在这个工作方式里最重要的事：判断标准从哪里来。讲者关心的问题不是"如何更快地重复"，而是"如何把标准定下来，然后让执行者按标准自我约束"。在他的表述里，一位主厨培养出的副厨需要理解菜单与标准，而不只是执行动作。

> ⚠️ **注意：误用工厂隐喻的两个后果**
>
> 第一，把注意力放在增加 agent 数量上，而忽略环境是否已经能约束它们；第二，把产量当作目标，于是把"提交了多少 PR"当成了质量指标。讲者在后面专门澄清，2,500 个 PR 里有相当比例是维护性工作，而不是 2,500 个新功能。

### 从独厨到副厨：分工的依据

讲者把这个问题还原成一个具体的自问：我怎样从"一个人做菜"变成"有几个副厨帮我"？关键在于分工的依据。他强调自己不是"为了分工而分工"，而是按能让整体效果更好的方式切分任务。他给出的对照是：如果一位副厨不只是做菜，还要负责组织整个厨房，那么对他的要求和工具配置就完全不同。

### 名字与声誉

讲者用另一个角度说明为什么"餐厅"比"工厂"贴切：你的名字仍然与你的作品绑定，声誉随之而来。因此"厨房怎么搭"这个问题的答案，会反过来影响别人如何看待你交付的东西。这一层在工厂隐喻里是缺失的，流水线上没有人会因为出货量而被记住。

### 本章小结

米其林厨房比软件工厂更适合描述这项工作，因为它同时容纳了标准、分工依据和声誉三件事，而工厂隐喻只容纳吞吐。这个选择有实际后果：它把注意力从"多开几个 agent"引导到"先把厨房搭好"。厨房搭好之后才有下一章的问题——在你无法逐一检查每道菜的前提下，什么东西能让你仍然放心？

## 验证：唯一能把自己从回路里拿掉的技能

如果这场对话只能留下一个结论，讲者给出的答案是验证（verification）。他说这是工具箱里最重要的技能，也是他花最多时间调校的部分。原因很直接：只有让 agent 能够验证自己的工作，人才能从回路里被拿掉。

### 为什么验证排在第一

验证的含义在讲者这里很具体：给 agent"手和眼"，让它能够运行代码、与结果交互，而不只是生成文本。他描述了自己加入 Cursor 后构建的第一个技能，也是真正让他沿着信任阶梯往上走的那一个。他的对照很明确——无论早先那些技能做得多好，只要"我"仍然是 agent 与产出之间的代理，阶梯就停在原地。

### 从自我验证到爬山

验证带来的第一个具体用法，是让他能够在性能工作上做"爬山"（hill climbing）。这个方法的构件只有两样：一个可以打分或判断的评分标准（rubric），以及一个可以反复迭代的循环。有了这两样，agent 就可以持续尝试改进，而不是等人来判断每一步。

讲者把这一思路与 Andrej Karpathy 公开发布的 Auto Research 联系起来，认为两者共享同一组想法。他也顺带提到自己对 Opus 5.5 这类前沿模型的评价，用来说明为什么"把评价标准交出去"变得可行。

### 验证技能成为关键基础设施

在团队层面，讲者的说法是验证技能已经变成关键基础设施，原因是每个人都在用。他提到每个应用都配有一个自动维护的验证技能，这类技能不断被更新，而不需要人手动同步。

> 🔑 **要点：验证的两层作用**
>
> 在个人层面，验证让 agent 可以自我检查，从而把人从判断回路里移出去。在团队层面，验证技能被持续维护并共享，于是它约束的对象从某一次任务扩大为所有人和所有 agent 的行为基线。第二层作用通常被低估，但它决定了这套方法能否在多人协作中稳定下来。

### 本章小结

验证之所以排在第一位，是因为它是唯一能改变"人在回路中的位置"的技能：有了可运行的判断标准，agent 才能自我检查，人才有资格往外退。爬山式的循环需要一个评分标准加一个反复迭代的循环，两者缺一不可。验证技能在团队内被共享并自动维护之后，它就从个人技巧升级为行为基线。接下来要处理的问题是：为了把验证做扎实，哪些部分不该再交给 agent 判断？

## 把确定性的部分交出去

讲者反复强调的一条设计原则，是把工作中确定性的部分从 agent 手里拿走，只把真正需要判断的部分留给它。这条原则既解释了他为什么写 CLI，也解释了 skill 的结构为什么长成现在的样子。

### 什么时候用脚本，什么时候用判断

他给出的划分方式是"梯度"：有些工作完全依赖判断，需要把多条上下文拼在一起思考；另一些工作高度机械，例如把代码从一种模式重构到另一种模式。后者不需要 agent 每次都重新思考并发明一个解法。

他把验证技能里的 CLI 归因于一个早期的具体困扰。当时社区最关心的是上下文窗口（context window）的管理，压缩与摘要的质量还不够好，甚至有一个流传的说法：一旦 agent 压缩过一次上下文，这次会话剩下的部分就会变笨。因此人们非常在意上下文用量的效率。这是他把验证技能中确定性部分编码成脚本或 CLI 的直接动机。

> ⚠️ **注意：一个反复出现的错误来源**
>
> 在没有 CLI 的时候，每个 agent 都会为了验证自己的工作而"重建一遍世界"，而且每个 agent 重建的方式都不一样。讲者观察到的代价有两层：不只是上下文被消耗，速度也被拖慢。更浪费的是前一个 agent 写出的可用脚本会被丢弃，下一个 agent 再写一遍。

### CLI 带来的三重收益

把确定性部分固化成 CLI 之后，收益可以分开计。上下文层面，agent 不再需要重新发明已有能力。速度层面，agent 不必再经历"写脚本、测试、失败、重写"这一轮。一致性层面，所有使用这个技能的 agent 共享同一段实现，于是同一件事每次都按同一方式完成。

### skill 是薄壳

讲者对 skill 本身给出的评价相当克制：skill 并不是什么新颖的软件，它只是与 Playwright、Chrome DevTools 协议以及若干 API 打交道的胶水。他更愿意把 skill 理解成一个外壳（wrapper）：里面放着少量说明，用来指导如何使用技能自带的自定义工具。

> 💡 **知识点：为什么把代码塞进 skill 反而让它更有用**
>
> 把确定性逻辑移到脚本里，等于替 skill 保存信息并让它保持小巧。agent 需要读的说明变少了，需要正确执行的动作变多了。这个取舍的方向与直觉相反——通常我们会认为"多写点说明"能让 agent 更听话，而讲者的经验是"少写说明、多给代码"更稳定。此外，当确定性和非确定性被分开之后，agent 才能真正被用在它被训练来做的那部分工作上。

### 这项原则的另一个适用场景

迁移与重构是这条原则的另一个例子。当他讨论如何从一种技术栈迁到另一种技术栈、尤其是迁到对 agent 更友好的方案时，主要手段是脚本与 CLI 这类确定性工具：代码修改（code mod）、遍历抽象语法树（AST）、以及机械式的代码变换。这些动作交给脚本按固定规则完成，而不是让 agent 每次临场判断。

### 本章小结

确定性与非确定性的分工回答了"哪些部分不该交给 agent 判断"这个问题：机械、可固定成规则的部分应当写成脚本或 CLI，只把需要权衡的部分留在 agent 手里。这样做同时降低了上下文成本和执行时间，并让同一件事每次都以相同方式完成。skill 在这种分工下退化为薄壳，只保留必要说明。下一章讨论这套分工在代码库层面的对应物：不是把规则写在说明里，而是让错误根本无法发生。

## 环境即约束：让错误不可能发生

讲者提出了一个身份判断：工程师的新工作重心是环境。他把环境的作用讲成约束——不是提醒 agent 不要犯错，而是让那类错误在结构上不可能出现。

### 好代码库的唯一标准

他引用的定义很短：好的代码库是容易改动的代码库，即改动时不容易把东西搞坏。这个定义落实下来就是大量护栏，以及把人和 agent 都限制在很窄的路径上。护栏不只在自动化检查这一侧（lint、类型检查等），也在抽象设计这一侧——团队甚至为 agent 专门构建了一个工作框架。

> 🔑 **要点：环境优先于提醒**
>
> 当某个错误反复出现时，把它写进说明是一类做法，把它变成约束是另一类做法。讲者选择后者，理由是约束不占用 agent 的注意力：agent 不需要"记住"规则，它会在碰到规则的瞬间被挡住。这个差别在长任务里会被放大，因为说明会随上下文被稀释，而结构不会。

### Dune：约定式目录与严格 lint

讲者介绍了一个内部框架 Dune，并给出一个便于理解的类比：它是团队 Electron 应用的内部版 Next.js。Dune 的设计目标是把"只有一种做法"写进结构里。

具体机制包括：每个功能有独立目录；有一条约定将功能代码组织在固定位置；由一个注册表（registry）通过扫描代码库来自动发现功能。配合非常严格的 lint 规则，这套组合让"写坏代码"变得困难。结果是双向的解放：人的注意力被释放，agent 也不必再思考"这段代码应该放哪里"。

### 从八个 God file 说起

这套目录约定有明确的起点。新项目 Grokbot 最早的几个版本由 8 个 God file 组成，每个文件至少有 10,000 行。讲者不得不把它拆成更小的部分。他从中总结出的做法是：观察 agent 如何失败，每当看到一次错误或一个本可以更好的做法，就退一步问——怎样把它变成一条 lint 规则，怎样让代码库让这件事不可能发生。

由此也解释了一个常见的困惑。主持人提到一个反讽：TypeScript 的类型定义文件据说只有 25 行，而讲者刚刚在讲 God file 的问题。讲者的回应承认了这个对照，并顺手提到那部分实现可能已经被改写。这个插曲恰好说明了同一原则的两个方向：结构约束的目标不是减少行数，而是减少"可以犯错的位置"。

### 类型收窄与约束空间

讲者把自己的思路追溯到早年学习 TypeScript 和类型系统的经历。他最喜欢的一个特性是类型收窄（type narrowing）：从一个宽泛到"可以是任何东西"的类型出发，通过类型守卫和运行时检查，逐步把可能空间收小，直到明确"这不是任意字符串，而是一个特定的常量"。他认为这种把可能空间压窄的做法，与代码库中的约束是同一种思路——两者都在减少存在歧义的选择。他甚至用范畴论来类比：限制可能存在的类型数量，直到只剩一种。

### 本章小结

环境的作用是把规则从"需要 agent 记住"变成"让 agent 撞上"。好代码库的定义是容易改动，实现手段是护栏加窄路径。Dune 用约定式目录、注册表发现和严格 lint 把"只有一种做法"写进结构；8 个至少 10,000 行的 God file 是这套约定的反面起点。类型收窄给出了同一个原则在类型层面的表述——压窄可能空间。环境搭好之后，剩下的问题变成机器如何在没有人的情况下持续接到任务。

## 两个循环：机器如何自己接到任务

讲者用内循环与外循环区分两类工作，并指出把两者连接起来是这套方法能否规模化扩展的关键。这是 2,500 这个数字背后真正的机制来源。

### 内循环与外循环的分界

按讲者的定义，内循环是他的"agent 工程师"按他的意图快照（snapshot of intent）在代码上工作；外循环则是外部系统中发生的事情——缺陷报告会出现在 Slack、Linear 或 X 上，而这些系统与内循环并不相连。因此外循环里产生的信息，长期以来必须由他本人搬运进内循环。

> 💡 **知识点：内外循环的关键差别在于信息是否会自动流回**
>
> 内循环的信息是自足的，外循环的信息不是。只要外循环与内循环之间没有触发器，人就会被固定在"信使"这个位置上，反复往返于 Slack、Linear 与 agent 之间搬运上下文。这与第二章的"肉代理"是同一个问题在不同层面的表现。

### 意图快照会过期

讲者用"快照"这个词是有意的：内循环依据的是意图的某个时刻的副本，而新信息随时可能出现——缺陷报告、功能请求、后端基础设施的限制。这些信息一旦出现，快照就开始过期，而更新快照的责任又落回人身上。他给出的解法是设立触发器把外部信息拉回内循环。

连接之后的形态很清楚：可以用 Slack 之类的 MCP 服务，也可以自建订阅。接入之后，agent 可以被告知"订阅这个频道，每当有相关缺陷报告就去分诊、复现"，而复现所依赖的正是前面已经建立好的验证技能。讲者的评价是，当两个循环连接起来时效果非常强，因为 agent 获得了自己获取上下文的能力。

### 幕僚长：一个不干活的 agent

讲者描述了一个特殊角色，他称之为 agent 的管理者、行政主厨或幕僚长（chief of staff）。这个 agent 本身不做事，它的职责是委派、编排并管理向它汇报的子 agent，同时负责把工作推进并把上下文传递下去。

它的价值在处理突发时最明显。假设某个时刻忽然涌来一批缺陷报告，数量可能在数十条量级，协调者可以判断如何把它们分派出去。讲者说它能够采用多种 agent 拓扑，自行决定怎样把任务高效地分发给团队。

这里还有一个反直觉的设计要点。人容易想到"一个任务对应一个 agent"，但讲者指出那样会丢掉任务之间的线索：多个 agent 可能重复劳动，也可能没有人看到更高层的问题。他的例子很具体——当你手上有几份略有差异的缺陷报告时，把它们放在一起看反而更有价值：单独看第一份报告时你以为缺陷在这里，看到其余报告之后才发现问题在更上层。

> 🔑 **要点：为什么"看起来低效"的并行反而更有效**
>
> 让多个 agent 同时处理同一批相关的缺陷，表面上像是重复投入，但它换来了跨报告的模式识别能力。这个收益只在任务被当作一组而不是一条时才出现，因此"任务分组"本身就是一个需要判断的决策，而不是一个可以省略的步骤。

### "我在哪里是瓶颈"

讲者把它提升为日常工作方式：不断追问"我在这个流程里是哪个环节的瓶颈"，以及"我的 agent 为什么需要我来回答这个问题"。目标不是让 agent 猜，而是让它用真实数据回答自己的问题。

他对"公司大脑"或"上下文图谱"这类流行说法给了一个务实的解释：这些概念既不复杂也不抽象，实质只是"把那些本来需要我亲自传递的信息，教给 agent 让它自己去取"。按他的表述，这些做法的作用就是把他自己从等式里移除。

### 本章小结

内循环按意图快照工作，外循环在 Slack、Linear、X 等外部系统里产生信息。两者之间如果没有触发器，人就固定在信使位置，意图快照也会持续过期。解法是让外循环的信息自动流入内循环，并引入不做事只委派的协调者 agent 来处理突发任务。任务需要按组处理而非逐条处理，因为跨报告的模式识别只在成组时才出现。核心自问始终是"我在哪里是瓶颈"。至此，机制链条已经完整，下一章看它产生的实际数字和代价。

## 2,500 个 PR 的实际构成

讲者在对话中主动澄清了这个数字容易被误读的地方，也给出了它的边界。这一章把数字放回它的来源和条件下。

### 不是 2,500 次对话，也不是 2,500 个功能

讲者否认"2,500 个 PR"意味着他手动发起了同样数量的对话。他给出的机制是：这些循环建立之后，他实际上是在并行地复制自己。他也提到自己并没有坐在那里创建 2,500 个会话。

其中有相当比例的工作属于"园艺"（gardening），也就是维护性工作，而非新功能。他强调 2,500 个 PR 并不是 2,500 个功能。

> ⚠️ **注意：数字的可比性问题**
>
> "提交了多少 PR"这个指标之所以不适合横向比较，有两个原因：第一，它混合了功能开发与维护性工作；第二，它依赖前置投入——环境与验证技能先搭好，同样的方法才可能产生这个数量。缺少前置条件时，把 2,500 当作目标会得到相反的结果。

### 让 agent 合并自己的代码

讲者认为真正的解锁点在于把问题倒过来问：怎样做到让 agent 能合并自己的代码。他提到在工具中开启"全自动驾驶"（full autopilot）会触发一轮非常严格、密集的验证循环：针对每个 PR 派生出一批验证 agent，并进行模糊测试（fuzzing）。这里的模糊测试有具体含义——实际运行应用、像真人一样点击和操作，寻找回归和实现中的缺陷。

他对这个组合的评价是：验证加环境，这两件事的组合让他能够退开，让 agents 去合并，而他在第二天早上通过查看提交历史来审查。如果发现问题，他会进去纠正：回滚、修改，或者新增 lint 规则。

### 抽样而不是逐一试吃

面对"2,500 个 PR 你怎么审查"这个必然的追问，讲者没有给出一个可以无限审查的答案。他承认不能处于"永远不再品尝自己的菜"的状态，但也指出在规模之下不可能逐一品尝，尤其是同时经营多家餐厅时。因此答案从"逐一审查"变成"抽样"，并把重点放在流程上。

他把这个角色类比为工厂里的质量监督员：无法检查每一件产品，所以每天抽样，非常严格地审查 agent 写出的代码，思考其中的低效与坏模式，然后修正环境而不是修正那一个 agent。他给出了判断依据——如果只是孤立的一次事件，也许没什么可改；如果多个 agent 在同一个问题上重复同样的捷径，把同一个临时方案到处传播，那就是修改厨房或工厂的信号——调整技能、约束、lint 与类型系统，让这个问题不再发生。

### 缓冲队列：先记录，后处理

讲者还给出一个与直觉相反的反例。他有一个 agent 持续扫描代码中不好的 React 模式，但他并不让它直接修，而是让它先把发现追加到一份文档里；每隔几天他再看一次，判断"这些其实是同一个问题"。他认为这种缓冲、队列式的做法有时比立刻派出一批子 agent 去修每一处更有效。

理由与判断力有关：当人处于纯执行模式、忙于尽快完成不断到来的任务时，容易看不到更大的图景。缓冲区提供了可以让人（或者一个 agent）用自己判断力去看的产物，从而找出本来会被逐条修复掩盖掉的那些模式。

另外，这也解释了幕僚长这类角色的第二个价值：它不仅能执行，还能看到森林，而不只是看到每一棵树。

### 本章小结

2,500 个 PR 既不是 2,500 次对话，也不是 2,500 个功能，其中包含相当比例的园艺工作；它依赖已经搭好的环境与验证技能，因此不具备直接横向比较的意义。让 agent 合并自己代码的前提是一轮严格的验证循环——为每个 PR 派生验证 agent 并做模糊测试，实际运行应用、寻找回归。审查方式从逐一检查改为抽样，并据此修正环境而不是修正单个 agent。缓冲队列把"立刻修"换成"先记录再判断"，以保住跨任务的模式识别。这些做法都有前置条件，下一章处理它们的边界。

## 边界：单向门、可验证性与"暗工厂"

一套方法如果不能说明自己在什么条件下失效，就不能被可靠地使用。讲者在对话后段给出了几处明确的边界，其中最重要的两条是可验证性与不可逆操作。

### "暗工厂"到底指什么

对话围绕"暗工厂"（dark factory）展开了一场澄清。讲者先说这是一间灯亮着的工厂，随后修正自己：在某种意义上它确实是暗的，因为如果 agent 能合并自己的 PR，那么在他睡觉的时候它就处在熄灯状态。

他给出的具体图景是：当他入睡时 agent 仍在工作，他拥有相当于十多个幕僚长的 agent，各自负责一个方向——一个负责 Grokbot 桌面应用的性能，一个负责修复用户报告的缺陷，还有一个在探索用另一种语言重写它，纯粹出于好玩。他强调后面那个只是玩具性质的尝试。

主持人在这里划出了一条重要的界线。他提醒，"暗工厂"容易与 Karpathy 的 vibe coding 混为一谈——后者的极端形态是代码几乎不存在。主持人的判断是讲者的方法完全不同：代码与环境是核心，代码与环境糟糕就会得到糟糕的输出，也就是垃圾进垃圾出。讲者对这一区分的回应是同意，并补了"调光开关"的说法；他更愿意回到餐厅的比喻，因为即使作为餐厅老板，你仍然会偶尔走进店里尝一口菜。由此他重申了"抽样而非阻断"的重要性。

> ⚠️ **注意：两种"暗"的区别**
>
> 一种"暗"意味着不再存在需要维护的代码与环境，另一种"暗"意味着环境已经足够强，可以让 agent 在无人值守时合并代码。两者的前置投入方向相反：前者忽略环境，后者把全部前期投入放在环境上。把它们混为一谈，会得出"这套方法不需要工程约束"的错误结论。

### 恐惧与第一步

讲者没有掩饰第一次开启无人值守时的心理成本。他说开启暗工厂的第一天非常可怕，担心自己会不会造成一次严重事故，或者在一个晚上之内把东西弄坏。他承认这需要相当大的勇气，并说自己现在状态好得多、睡得更好了，而在他讲话的同时 agent 正在合并代码。

### 单向门与双向门

主持人提出了这套方法在受限行业里最尖锐的问题。他借用一个区分：有些 PR 是双向门——合并之后还能回退；另一些是单向门——会造成数据丢失或某种不易回头的结果。问题在于，如果你面对的项目里大多数 PR 都是单向门，这套方法还能不能用。

讲者的回答是，这最终取决于你能否从 agent 那里获得足够质量的验证，并且把可验证性提升为前提条件。当一个领域的工作可以被验证时，单向门在某种意义上会变成双向门。反过来，如果一项工作很难被程序化地验证，那么要达到这一步就非常困难。

他也顺势给出自己的判断依据：软件工程之所以适合这套方法，是因为它在很多情况下可验证，尽管不是全部；数学是另一个例子——不是所有部分，但某些部分在写出证明之后是可验证的。他坦承这是一个自己并没有完整答案的好问题。

> 🔑 **要点：方法适用的底层条件**
>
> 这套方法的适用范围不取决于任务大小或团队规模，而取决于工作是否可验证。可验证意味着存在一种可以自动运行、并给出可信判断的检查方式。验证质量决定你能否无人值守，而领域是否可验证决定验证质量的上限。这个条件先于一切工具选择。

### 把证明带进语言

讲者对未来的预测集中在这一点上：会出现越来越多面向 agent 的编程语言。他举了一个自己见过的最有意思的例子——一门叫 Bend 的语言，它把编程与证明结合起来。

他为不熟悉的读者补了背景：证明的意思是可以用数学方式形式化地验证代码正确，尤其在代码以函数式风格编写时更自然。长期以来，这类工作必须在另一种语言里完成，例如 Lean 或 TLA+：先构造数学证明，再用求解器检查是否覆盖了所有情况、是否存在竞态条件。他把结论压缩成一句话——如果它能编译、如果证明显示它是正确的，那为什么还要犹豫合并它。当然，他补充说并非所有领域都可验证。

### 本章小结

"暗工厂"的准确含义是环境足够强，可以在无人值守时合并代码，而不是不需要维护代码。第一次无人值守的心理成本很高，讲者如实描述了这种顾虑。单向门与双向门的问题把方法的边界暴露出来：当工作可验证时，单向门在某种意义上变成双向门，而不可验证的领域很难走到这一步。讲者对未来编程语言的预测是证明与编程结合，并提到 Bend、Lean 与 TLA+ 作为例子。边界明确之后，还有一个更基础的问题：技能本身到底是什么。

## 技能到底是什么

对话接近尾声时，双方回到最基础的层面，讨论技能的定位、形态变化，以及个体应该如何构建自己的技能集合。这一部分包含讲者对方法论走向的判断。

### 技能是流程的语言化

讲者的定义很短：技能是从流程派生出来的东西，是把流程变成文字。主持人补充自己的说法：技能本质上就是英语或者某种语言，就是 Markdown。讲者同意，并进一步说明技能与工具是互补的，可以按个人需要交织在一起使用。

### 技能在变小

讲者观察到一个变化趋势。去年的技能更偏向实现细节，例如明确规定应该使用哪些脚本命令。随着模型能力提升，这些部分可以直接删掉，只保留流程本身。技能因此变得像一系列步骤、一连串你自己的流程，并且这个趋势会继续——技能会越来越小、越来越紧凑。

> 💡 **知识点：为什么技能可以变薄**
>
> 技能变薄的前提是模型自己具备了实现细节的能力。当模型还不足时，把具体命令写进技能是必要的补偿；当模型足够强时，同样的内容反而变成约束与噪声。因此"技能应该写多厚"不是风格问题，而是随模型能力变化的取值，需要定期重新评估。

### 你自己的历史对话是矿

主持人提出了一条他认为非常实用的建议：回头查看自己过去与 agent 的对话记录，从中挖掘信息——特别是那些你不得不反复介入、反复纠正的地方，把这些更高层次的收获变成可复用的技能，让 agent 不再重复同一个错误。他用的措辞是"宝库"（treasure trove），因为那些记录里的流程是已经物化了的、真实的流程。

讲者认同这一建议，并给出一个具体的来源。他曾经处理 Cursor 应用的虚拟化问题，缺陷很多；每开一个新会话，他都觉得上一个会话里有大量有价值的上下文，希望把它带过来。这个需求催生了查看历史对话的做法，随后他把这个工作流压缩成一个叫 recall 的技能，从此不必每次写一大段说明。他还提出另一种用法：让一个 agent 去通读你的历史记录，找出你反复介入的模式，再建议把它们变成 lint 规则或新的技能。

### 每个人自己的刀

讲者回到烹饪比喻，指出它之所以贴切，是因为每位厨师换工作时都会带上自己的刀——工具是跟着人走的。由此他给出对"信任"的另一种解释：信任实际上是人对自己的工具的信任；当你在磨刀和理解工具上花了时间，你就能做出很好的东西。

他也承认每个人的技能与工具组合都会不同：有人可能把主持人的某个技能与 pstack 里的执行类技能组合起来效果很好，另一些人则可能更依赖其中一方的技能。他的建议是把两人的技能都读一遍，然后组合成自己的版本，因为技能的优点正是可塑性——它就是语言，其中唯一称得上神奇的东西，是把抽象流程变成语言时所做的那些思考。

### 本章小结

技能是从流程派生的语言产物，本质上就是 Markdown 文本。它的形态正在变小：模型能力上升之后，原本必须写进技能的实现细节可以直接删除，只留下流程本身。构建个人技能集合最可靠的原料是自己的历史对话，尤其是那些反复介入和纠正的位置；把这类重复提炼成技能、规则或 lint，可以终止同类错误的重复发生。工具应当跟随个人而非绑定团队，信任在本质上是人对自己工具的信任。最后一章收束全书。

## 总结与延伸

这场对话的实质是一份把"人从回路里拿掉"的分阶段说明书。讲者的路径可以压缩成一条依赖链：先承认瓶颈在人这一侧；再承认领域专长的价值转移到了意图表达上；然后建立验证能力，让 agent 能够判定自己的工作是否成立；接着把确定性部分固化为脚本或 CLI，只把判断留给 agent；再用代码库结构与环境约束让错误无法发生；最后把外循环的信息接进内循环，让人不必再充当信使。

这条链上真正不可替换的环节是验证。讲者的说法很有代表性：验证与环境这两件事的组合，才是他能够退开、让 agent 自行合并代码的原因。反过来说，如果没有可运行的检查方式，"无人值守"只会变成"无人知道"。

讲者自己划出的边界同样重要。抽样审查取代逐一审查，是因为规模使后者不可能；缓冲队列取代立即修复，是为了保住跨任务的模式识别；单向门与双向门的区分说明了方法在不可逆操作面前的极限。他给出的底层条件是领域可验证性，而不是任务规模或工具选型，并且坦承这一点并非所有领域都满足。

本讲义在整理时做了两处显式处理，以便读者判断可信度。第一，源音轨是英文播客访谈，B站页面标题为中文，因此本讲义是从英文转写翻译整理而成的中文笔记；转写过程中还出现过一次语言参数写错导致的整轮返工，最终字幕为英文转写。第二，用户明确要求只做音频文字提取、不使用视频，因此本讲义不含任何视频画面，也就没有可在画面间核对的讲者视觉物料——所有论述均来自口语内容。

可以带走的具体做法有四项。其一，选择验证方式时先问"这项工作的结果能不能被自动判断"，而不是先问"用哪个 agent"。其二，把反复出现的错误从说明中移到结构里，让它在发生之前就被挡住。其三，把确定性的部分写成脚本，让 skill 保持薄。其四，定期回读自己与 agent 的历史对话，找出反复介入的位置，并把它们变成技能或规则。

一个仍然开放的问题由讲者本人提出，并且他明确表示自己也没有答案：对于那些难以程序化验证的领域，例如部分医学、法律与金融工作，这套方法的入口在哪里。他的预测是会出现更多把证明与编程结合的语言，从而把一部分不可验证的工作变成可验证的；这个预测是否成立，取决于这类语言能否在真实工程中普及。
