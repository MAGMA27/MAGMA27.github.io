# DeepSeek Superagent 架构拆解：让编程 Agent 成为团队的一员

DeepSeek Harness 在设计文章中提出：单个任务的上限往往受模型能力约束，多任务协作的瓶颈则逐渐转向人的注意力。人需要在多个会话之间切换、记住上下文，并反复转达同一任务的新进展。

一个编程 Agent 能修复一个问题，并不意味着它能在团队里长期工作。团队场景还需要回答：谁可以给它派活？它如何判断一条消息是否值得行动？有人继续评论时，应该交给原任务还是创建新任务？进程重启后，怎样避免重复操作？

[DeepSeek dsh-superagent](https://github.com/deepseek-ai/dsh-superagent-prototype) 把这些问题放到同一套工作流中：监听 GitHub 和可选的飞书事件，经授权判断后创建工单，交给独立的执行会话，最后回到原来的对话交付结果。

> **阅读范围**：本文结合 DeepSeek Harness 官方发布的[设计文章](https://x.com/DeepSeekHarness/status/2116857257245987236)（[可访问的英文转载](https://xitter.cf/DeepSeekHarness/article/2116857257245987236)，注明为中文原文的机器翻译）和仓库快照 [`6337fc8`](https://github.com/deepseek-ai/dsh-superagent-prototype/tree/6337fc823ce20251c8de8085948165c81aaa701e) 中的文档和实现整理。仓库明确说明这是研究原型，不是官方产品或生产就绪软件；公开版本也不完全等同于内部版本或相关文章中的设计，部分文章所述方向尚未在原型中实现。下文明确区分设计文章的设想与公开仓库的实现。

## 从一条消息到一个工单

假设团队成员在 GitHub Issue 中要求 Agent 修复一个缺陷：

1. **Source 接收事件**：GitHub 来源读取通知或订阅内容，过滤自己的消息，将外部事件转换为 Trigger。来源保存读取位置，避免重启后无意义地重复消费。
2. **Thread 聚合上下文**：同一个 Issue 或讨论中的事件按线程组织。同一线程同时最多运行一个 Eval，期间新到的事件可合并进入下一批。
3. **Eval 做两层判断**：先由确定性的 Gate 根据来源策略、发送者和接收范围决定是否准入及请求强度；再由主 Session 对需要研判的候选事件结合规则与上下文作出判断。
4. **接单时记录授权**：接受后创建 Ticket，并附上 Mandate，记录范围、强度、策略版本及依据。一个线程可以有多个独立工单，避免把所有讨论误认为同一件事。
5. **Assignment 交给执行器**：执行器获得该工单的会话与工作目录，读取原始上下文、实施修改、验证，并通过原渠道回复或提交 PR。
6. **后续消息进入订阅**：Issue 或 PR 上的新消息可以进入已订阅的工单。执行器处理授权范围内的后续要求；超出范围或属于其他任务的请求会交回，待没有其他工单负责后重新评估。

这一流程不是简单地把每条消息都转成一个 prompt。Trigger、Decision、Mandate 和 Ticket 分别保留事件、判断、授权和工作状态，让人可以追溯系统为何行动。参见[授权文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/002-authorization.md)。

## 授权：先判断能不能做，再判断值不值得做

![事件先经快速过滤和语义研判，已订阅线程的后续消息直达原任务](https://free.picui.cn/free/20258/2026/11/05/6aec880ee220e.png)

明确请求与推断候选的区别，是系统控制自主程度的关键。允许名单中的人直接呼叫 Agent 是明确请求；符合来源配置的其他消息或允许的机器人消息，可能成为推断候选。具体结果取决于来源、接收范围、名单和准入表，不能只看消息里有没有 @。

对于推断候选，项目提供三种接单模式：

| 模式      | 行为                                                       |
| --------- | ---------------------------------------------------------- |
| `off`     | 不把推断事件作为候选；明确请求仍可处理                     |
| `observe` | 默认模式。进行研判并记录“本会接单”的结果，但不自动创建工单 |
| `auto`    | 研判通过且匹配启用的规则时，可以自动接单                   |

这使团队能先检查观察记录，再决定是否开放主动接单。自动接单并不意味着 Agent 自己发明工作：推断任务必须有匹配规则，工单的 Mandate 也会记录对应规则和范围。

**上下文不等于授权。** 订阅线程中的 CI 结果、机器人评论和人的补充说明都可能送进工单，但消息本身不能改写 Mandate。策略变化会使正在进行的评估重新排队，并通知受影响的运行中工单；它不会直接取消这些工单。已结束工单恢复前，系统会重新验证其授权是否仍然有效。

## 主 Session 与执行器：路由和干活分开

主 Session（代码里称 `orchestrator`）负责评估、路由和协调，而不是亲自完成每个修复。它接收候选事件、工单报告和后续通知，再把原始事件及路由信息交给执行器。执行器（`worker`）负责理解具体问题、检查仓库、修改、验证和交付。

每个 Ticket 对应一个执行 Session 和工作目录；准备命令可以创建 Git worktree。并发受 worker slot 限制，人的消息或状态请求可以使用额外的一个 slot，避免新任务占满资源后，已有任务无法响应人。长时间后台任务会影响 slot 的占用，交接给人时则按运行状态释放。

这里的“独立目录”是工作组织方式，**不是安全沙箱**。文档说明执行器以操作者的操作系统用户身份运行命令，默认无需逐条批准；命令包装和阻止列表也不是完整安全边界。实际部署需要自行约束账户权限、凭据、执行环境和仓库访问。参见[执行文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md)。

## 工程实现：状态先落盘，外部动作随后执行

从代码结构看，`Runtime` 负责组装、启动和关闭；`Engine` 是 Trigger、Thread、Decision、Ticket 和 Assignment 的唯一写入者。Engine 在事务中更新领域状态，并安排外部工作；适配器在事务提交后处理实际副作用。持久化使用 SQLite，状态目录有进程锁。[架构文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/007-architecture.md)还列出了 Source、Assessor、Executor、Outbox 等边界及其对应模块。

这套安排解决的是长任务的可靠性问题，而不是保证外部世界的所有操作恰好执行一次：

- **事件去重与串行评估**：同一 Trigger 不重复创建工单；每个 Thread 的评估有序进行。
- **消息持久化与重试**：出站消息先记录，再通过 Outbox 发送；失败按退避策略重试，同一工单发往同一对话的消息通常保持顺序。
- **重启恢复**：被中断的 Assignment 可以重新启动，并提示执行器先检查目录、Git 历史和 GitHub，再重复外部操作。未被会话读取的输入会重新交付。
- **阻塞与人工接管**：执行器报告 `blocked` 或 `failed` 后，自动输入不会继续唤醒它；人的消息或手动重试可以解除等待。
- **策略变更可追溯**：评估和授权记录各自依据的策略版本，避免把旧规则下的判断直接当成当前判断。

## 设计文章补充：上下文、异步与长期运行

设计文章将 Super-agent 的目标归纳为持续、能并行推进任务、主动和长期在线。Router / Worker 只是其中一部分；它还借用了几种经典的系统设计思路。

**把上下文当缓存。** 文章将常用、近期相关的信息直接放进上下文（Inline），把过长或不常用的内容留在外部，只保留摘要和引用，需要时再读取（Spill）。事件、线程与会话通过 ID 相互关联，Router 可以从当前事件沿引用逐步找回历史，文章称之为 Chain of Recall。这是对上下文预算的管理，不等于模型能无限记住所有对话。

**让耗时操作在后台运行。** 文章提出异步 ReAct：启动长任务后，前台不必等工具完成；结果稍后作为事件送回。在原型中，长时间 shell 命令会转为后台任务，执行器可在后续步骤接收新消息。当前模型推理步骤仍须结束后才能处理新输入，因此不能理解成任意时刻都能打断模型。

![设计文章中的计算、状态、执行环境解耦与 Watchdog](https://free.picui.cn/free/20258/2026/11/05/6aec880f082b7.png)

**把长期在线拆成三个边界。** 上图是设计文章提出的方向：Agent Loop 的计算、持久化状态以及实际执行命令的环境可以分开，进而支持云端计算与连接自有设备；独立 Watchdog 还要检查系统故障和任务是否偏离目标。这些是设计文章的系统架构设想，不能据此断言公开原型已经提供完整的云端 BYOM 和独立 Watchdog。公开原型可核实的是本机状态持久化、失败重试和重启恢复。

**主动行动也需要有价值的交付。** 文章以后台复现问题为例：Agent 可以先投入计算，只有确认问题并找到合适修复时才交付，否则保持安静。这是文章描述的内部实践；公开原型是否执行主动任务，仍由接单模式和匹配规则约束。

## 实验说明：延迟与资源的交换

设计文章报告了一组初步调度实验：每轮约 300 条混合消息，其中约 20 条是工作请求，代码工作由耗时工具模拟；每种设计只运行 5 次。因此它衡量的是该合成负载下的调度与协调，不是实际编码能力的通用基准。

| 设计                     | 完成时间 p50 / p95 | 每轮缓存读取 token |
| ------------------------ | ------------------ | ------------------ |
| Super-agent，含直达      | 12.4 / 15.7 分钟   | 23.2M              |
| Super-agent，无直达      | 12.6 / 15.5 分钟   | 31.8M              |
| 单 Session，普通委派提示 | 20.4 / 29.5 分钟   | 6.1M               |
| 单 Session，优先委派提示 | 13.8 / 29.0 分钟   | 10.8M              |

在这组实验中，多会话以更多缓存读取换取更低、更稳定的完成时间；去掉后续事件直达并未明显改变完成时间，却增加了 Router 的决策与 token 消耗。样本量、模拟任务和具体提示都会影响结果，不应外推为真实项目必然获得同样的加速。

## 人在哪里介入？

管理面板首先呈现需要人处理的工单，然后展示系统健康和历史。用户可以从 Trigger、Eval、Execution 等视图追溯事件、判断原因、授权范围、执行状态和待处理问题，也能配置来源、规则、并发、提示词和部署参数。

执行器可以在结构化报告中提出需要人决定的问题。除此之外，项目希望消息尽量围绕可使用的结果或明确的人工动作：例如交付可审查的 PR、请求缺失资源，或说明任务被阻塞。面板设计见[项目文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/005-panel.md)。

提示词负责团队沟通、交付习惯与角色分工，但硬性授权、工具参数检查和账户包装由宿主代码执行；外部 Issue、评论或引用文档不能通过文字改变这些权限。自动合并则是一个需要特别区分的例子：仓库的默认条件写在交付提示词中，不是宿主的专用合并判定逻辑；要强制审批等约束，应依赖 GitHub 分支保护等外部机制。详见[提示词](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/004-prompts.md)与[执行文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md)。

## 值得借鉴的设计

这个原型最有启发性的地方，是把 Agent 的自主性拆成可以分别检查的环节：事件是否进入系统、来源是否有资格提出请求、规则是否支持主动行动、工单具体获准做什么、执行结果是否需要人接手。它用订阅保持持续上下文，用 Mandate 限定行动范围，再用持久状态和恢复机制连接长时间运行的任务。

它适合拿来研究团队级 Agent 的领域建模和工作流，但不应直接推断为通用的生产系统：公开仓库面向一个 GitHub 仓库，依赖 DeepSeek Harness 及配置的外部服务；其安全边界和实际权限仍由部署环境决定。对准备实践的团队，先从明确请求和 `observe` 模式积累决策记录，是理解系统行为的一个可操作起点。
