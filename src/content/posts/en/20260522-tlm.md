# Byte-Pair Encoding

## What is it?

BPE is one of the mainstream methods used for tokenization in modern large language models.

## Why do we need it?

Let us start with the problem. The goal of an LLM is to take text as input and produce text as output, but the model operates through mathematical computations. Therefore, the text must first be converted into numbers for calculation.
There are several natural ideas:

1. Assign one ID to each character. The drawback is that the text sequence becomes very long. This is especially true for English text: "hello" would take up five tokens. The computational complexity of the Transformer's attention mechanism is proportional to the square of the sequence length (O(N²)), so excessively long sequences greatly slow down training and inference.
2. Assign one ID to each word. The drawback is that the vocabulary becomes enormous. More critically, the model can only understand words it saw during training. Once it encounters a new word, a spelling mistake, a technical term, or internet slang, it is helpless.

We therefore need a method that avoids these drawbacks.

## How does it work?

Unicode is a huge dictionary covering many languages. It defines encoding formats such as UTF-8, UTF-16, and UTF-32. UTF-8 has become the mainstream standard on the internet because of its efficiency and compatibility. BPE also typically uses UTF-8 encoding. Here is an example.
Suppose we want to encode "hello":

1. First split the word into a byte stream [b'h', b'e', b'l', b'l', b'o']. For Chinese and some special characters, a single character is encoded using multiple bytes, and the bytes of that character are also split individually.
2. Find adjacent byte pairs [b'he', b'el', b'll', b'lo'] and extract the one with the highest frequency. If multiple pairs have the same maximum frequency, the usual choice is the first one encountered or the lexicographically larger one. Here we choose b'he'.
3. Update the byte stream to [b'he', b'l', b'l', b'o'].

Repeat this process while maintaining a `merges` table that records each merge rule, such as [b'h', b'e']. Maintain a `vocab` table in which IDs 0–255 correspond to bytes 0–255, preserving the base bytes. Extend the vocabulary with merged bytes using subsequent IDs, such as [256: b'he'], until the vocabulary reaches the target size.
This keeps both the sequence length and vocabulary size more manageable. Because every word is first encoded with UTF-8, even an unseen word can be represented using the base bytes from 0 to 255. Semantically, however, an individual token does not necessarily have a clear meaning.

## Implementation details

1. Before processing, pre-tokenize the text, handling punctuation, spaces, newlines, and other characters correctly, and use a dictionary to count `{word: occurrence count}`.
2. Suppose the target vocabulary size is 5,000. The initial vocabulary contains 256 base bytes plus special tokens such as `[end_of_sequence]`. First count the occurrences of every pair by iterating over `{word: occurrence count}` and recording the counts in `{pair: occurrence count}`, then find the most frequent pair.
3. After adding the most frequent pair to the `merges` table, `{pair: occurrence count}` must be updated. One option is to iterate over `{word: occurrence count}` again and process each word according to the merge rules. A better approach is to update incrementally by maintaining an additional dictionary that records `{pair: words}`. This tells us which words are affected by each update. Find the `{pair: words}` entries related to the current update, iterate over the key-value pairs for the affected words in `{word: occurrence count}`, count the changed pairs and their occurrences, update `{pair: occurrence count}` and `{pair: words}`, and remove pairs that no longer exist. This updates the statistics efficiently.

# Tokenizer

Based on the BPE details above, the Tokenizer's job is essentially to:

1. Convert the text into bytes and merge them according to the `merges` table from the BPE stage.
2. Look up the corresponding number (token ID) in the `vocab` table and convert the text into numbers.

## Implementation details

1. The text must likewise be pre-tokenized first: the input is a string and the output is a list.
2. Merge the bytes of each token according to the `merges` rules. The brute-force approach is to iterate over the `merges` table and then over the entire pre-tokenized list, using nested loops. A faster approach is to maintain a `{pair: list[index]}` dictionary. Use the `merges` table to obtain the indices in the pre-tokenized list, replace the contents of that list according to the rules, then count the new pairs and update the `{pair: list[index]}` dictionary. Finally, remove the pair involved in this merge from the dictionary.
3. For large texts, use streaming processing. The resulting data of token IDs should also be stored in a format that is easy to process as a stream for subsequent training.

# Transformer language model

## PyTorch vector and matrix operations

In linear algebra textbooks, vector and matrix operations are generally written as $y = Wx$, where $x$ is a column vector. In computers, however, $x$ is usually created as a row vector. To stay consistent with the mathematical definition, vector-matrix multiplication in PyTorch is defined as $y = xW^T$. Taking a linear neural network as an example, the matrix is actually stored with `out_dim` rows and `in_dim` columns; it is only transposed during computation.

## Rotary Positional Embeddings (RoPE)

The idea behind RoPE is to encode each token along the embedding dimensions and perform one rotation for every pair of dimensions. The rotation angle is determined by the sequence position and the position within $d_k$. Like moving the hands of a clock, it rotates hidden features at different positions. On the one hand, this ensures that positional encodings do not repeat; on the other hand, no matter how the absolute positions of two tokens change, as long as their relative position stays the same, the angle between them remains the same, improving stability and generalization. It combines the parallelizability of absolute positional encoding, the length extrapolation ability of relative positional encoding, and the efficiency of having no additional parameters.

In the implementation, the rotation matrix depends only on position, so it can be precomputed during initialization and directly indexed later. The computation for each pair of parameters is $y_out = [x_1*cos - x_2*sin, x_1*sin + x_2*cos]$. Therefore, the odd and even columns can be selected first, the result can be computed with matrix operations, and the columns can then be concatenated and returned.

RoPE is mainly applied to the Q and K matrices. During the dot product, only the relative position $m-n$ remains in the parameters; the independent absolute positions $m$ and $n$ cancel out during the computation, allowing the model to naturally understand "distance" rather than "coordinates". The benefit is that positional information is successfully embedded without the misleading effect of absolute positions, so the model does not fail to recognize something merely because it moved to a different position. Applying RoPE directly to Q and K also preserves the original semantic information in the embedding space, so the model does not have to learn how to disentangle positional information from the semantic space.

## Numerical stability tricks in softmax

The formula for softmax is
$$softmax(x)_i = \frac{exp(v_i)}{\sum_{j=1}^n exp(v_j)}$$
The range of $exp(v_i)$ is [0, +inf). When the exponent is large, it can exceed the numerical limit. For stable computation, $v_i$ is usually reduced by the maximum value in the data, $v_{max}$, keeping the exponent in the range (-inf, 0] and preventing the value from overflowing.

## Why does dot-product attention divide by $\sqrt{d_k}$?

1. The value of the dot product grows with the dimensionality: $QK^T$ computes an inner product over $d_k$ dimensions.
2. Large values make the softmax gradient vanish: the softmax function outputs probabilities close to 0 or 1 for large input values. The gradients at these positions then become very small, making the model difficult to train and potentially causing vanishing gradients.
3. Dividing by $\sqrt{d_k}$ scales the result into a reasonable range, closer to zero. This keeps the softmax function in a region with moderate gradients and sensitivity to input changes, stabilizing training while preserving its ability to distinguish between different attention weights.

## Multi-head attention

Split $d_k$ to learn different semantic features separately, then concatenate them and pass them through a linear layer to combine the features.

```python
Q = rearrange(Q, "... sq_l (h d) -> ... h sq_l d", h=self.h)
K = rearrange(K, "... sq_l (h d) -> ... h sq_l d", h=self.h)
V = rearrange(V, "... sq_l (h d) -> ... h sq_l d", h=self.h)

Q = self.rope(Q, token_positions=token_positions)
K = self.rope(K, token_positions=token_positions)

attention = scaled_dot_product_attention(Q, K, V, mask=causal_mask)
attention = rearrange(attention, "... h sq_l d -> ... sq_l (h d)", h=self.h)

output = self.O(attention)
```

## Transformer layer

A complete Transformer layer is $y = x + MultiHeadSelfAttention(RMSNorm(x))$.

## The pre-training objective of an LLM

During pre-training, suppose the training material is a sentence containing 10 tokens. The input is the first 9 tokens, and the targets are the following 9 tokens. In the final layer of the model, `lm_head` transforms a $9*d_k$ matrix into a $9*vocab_size$ matrix. It then computes softmax, turning the problem into a classification task whose objective is to maximize the probability of the targets.

## Numerical stability tricks for cross-entropy

As a loss function, cross-entropy measures the difference between two probability distributions. Here, the ideal probability of the targets is set to 1 and all other probabilities to 0, so the model is trained to approach this distribution.

Cross-entropy needs to compute -log(softmax(logits)). Direct computation causes problems: if x is large, exp(x) overflows and becomes inf; if x is very small and negative, exp(x) underflows and becomes 0, after which log(0) becomes -inf.

The following expression is mathematically equivalent, so the solution is to transform the calculation into the expression on the right and then compute it. Finally, take the token-level average so that each prediction receives attention.
$$log(softmax) = log(\frac{exp(x_i)}{\sum_{j=1}^n exp(x_j)}) = x_i - log(\sum_{j=1}^n exp(x_j))$$

## The internal structure of an optimizer

| Property       | Data type    | Purpose and description                                                                                                                                                                                                                                                                                            |
| :------------- | :----------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `param_groups` | `list[dict]` | Parameter-group management. This is the core structure through which the optimizer interacts with model parameters. Each dictionary in the list represents a group of parameters, containing `'params'` (the concrete parameter list) and hyperparameters specific to that group, such as `lr` and `weight_decay`. |
| `state`        | `dict`       | State management. This stores the state of each parameter during updates, such as momentum buffers and historical sums of squared gradients. The key is usually the parameter object itself, and the value is a dictionary containing state tensors.                                                               |
| `defaults`     | `dict`       | Default hyperparameters. This stores the default configuration provided when the optimizer is initialized. When a parameter group does not specify a particular hyperparameter, its default is taken from here.                                                                                                    |
